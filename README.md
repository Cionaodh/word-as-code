# Прогнозирование прибытия вагонов

Статья собирается из Markdown в Word одной командой Pandoc.
Оформление хранится в `reference.docx` и редактируется через стили Word.


## Запуск на Windows

Нужны Windows 10/11 x64 и Pandoc **3.12.1**.

1. Скачайте [официальный Windows ZIP Pandoc 3.12.1](https://github.com/jgm/pandoc/releases/download/3.12.1/pandoc-3.12.1-windows-x86_64.zip).
2. Распакуйте архив. Папку с `pandoc.exe` поместите в проект под именем
   `pandoc`, сохранив остальные файлы пакета.
3. Откройте папку проекта. В адресной строке Проводника введите `cmd`.
4. Выполните:

   ```bat
   build.cmd
   ```

Результат — **[article.docx](article.docx)** в корне проекта.
Если Pandoc доступен через PATH, папка `pandoc/` не нужна.

При установленном GNU Make та же сборка запускается командой `make`.
Команда `make clean` удаляет готовый DOCX.

## Как устроен проект

Основная команда:

```bat
pandoc --defaults=document.yaml
```

В `document.yaml` указаны порядок разделов, выходной формат и путь к
`reference.docx`. Pandoc объединяет текст и применяет стили шаблона.
Внутри шаблона находятся образцы абзацев и таблицы; их текст в статью
не переносится. Pandoc записывает результат сразу в `article.docx`.
При повторной сборке существующий файл перезаписывается.

| Файл | Назначение |
|:-----|:-----------|
| `src/00_header.md` | УДК, автор, название, аннотация и ключевые слова |
| `src/01_intro.md` | Введение, объект исследования и действующий алгоритм |
| `src/02_data.md` | Подготовка данных и четыре исходных рисунка |
| `src/03_model.md` | Признаки, математические модели и формулы метрик |
| `src/04_results.md` | Обучение, таблица результатов и временная проверка |
| `src/05_conclusion.md` | Использование прогноза и заключение |
| `src/06_references.md` | Список литературы и строка авторского права |
| `images/` | Исходные изображения PNG |
| `reference.docx` | Стили Word и параметры страницы |
| `document.yaml` | Порядок разделов и параметры Pandoc |
| `build.cmd` | Запуск Pandoc на Windows |
| `Makefile` | Вызов сборки и очистки через GNU Make |
| `.github/workflows/build.yml` | Проверка сборки и публикация DOCX в релизе |
| `.github/dependabot.yml` | Ежемесячная проверка версий GitHub Actions |

## Как редактировать

Содержимое меняйте в `src/*.md`, сохраняя UTF-8. Новую главу добавляйте
в `input-files` файла `document.yaml`. Заголовки задаются через `#` и `##`,
формулы — через `$...$` и `$$...$$`, таблицы — обычной Markdown-разметкой.
Оглавление не создаётся.

Для изменения оформления откройте **`reference.docx` в Word**.
На вкладке **Главная → Стили** найдите нужный стиль, нажмите на него правой
кнопкой и выберите **Изменить**. При необходимости откройте всю область стилей
сочетанием **Ctrl+Alt+Shift+S**. Сохраните шаблон и повторите `build.cmd`.
Сетку и поля ячеек меняйте в стиле `Table` на вкладке конструктора таблиц.

| Стиль | За что отвечает |
|:------|:----------------|
| `Normal` | Основной шрифт, интервал и абзацный отступ |
| `UDC`, `AuthorBlock` | УДК и сведения об авторе |
| `Title`, `TitleLast` | Две части названия статьи и интервалы вокруг него |
| `Abstract`, `Keywords` | Аннотация и ключевые слова |
| `Heading 1`, `Heading 2` | Заголовки разделов |
| `Figure`, `Captioned Figure` | Размещение рисунков |
| `Image Caption`, `Table Caption` | Подписи рисунков и таблиц |
| `Compact`, `Table` | Абзацы в ячейках, сетка и оформление таблиц |
| `Copyright` | Строка авторского права |

Поля и формат бумаги меняются на вкладке **Макет** в `reference.docx`.
Размеры рисунков указаны рядом с ними в `src/02_data.md`.
Pandoc автоматически уменьшает слишком широкие рисунки до ширины области текста.
Имена стилей сохраняйте: по ним Pandoc связывает Markdown с оформлением.
Изменения только текста образцов внутри шаблона не меняют текст статьи.
Полужирное и курсивное выделение отдельных фрагментов задано в Markdown.

Образец оформления — исходная статья
«ГорлановДС_ДзгоевАЭ_Статья_в_сборнике_конференции.docx»:
A4, поля около 2 см, Times New Roman 14 пт, интервал 1,2, первая строка 1 см,
основной текст по ширине, подписи рисунков курсивом 13 пт. Таблицы имеют
полную сетку. Сведения об авторе, основной текст и четыре рисунка сохранены.

Статья дополнена формулами, таблицей признаков, таблицей ошибок и пояснениями
по временной проверке и использованию прогноза. MAE 21,15; 20,85 и 20,70 часа
перенесены из оригинала. Для действующего алгоритма в нём приведена
«средняя ошибка 3 дня» без уточнения определения метрики. В таблице это
различие пояснено. Ошибки в сутках получены делением часов на 24 и округлением
до двух знаков. Сборка не обучает модели и не пересчитывает эксперимент.

Список литературы и номера ссылок записаны в Markdown. При добавлении
источника проверяйте соответствие номеров ссылок и записей списка.

## Публикация на GitHub

1. На GitHub создайте пустой репозиторий: **New repository**. Оставьте создание
   README, `.gitignore` и лицензии выключенным — исходные файлы уже подготовлены.
2. Откройте `cmd` в папке проекта. Выполните команды, заменив `LOGIN/REPO`
   на свой адрес, показанный GitHub:

   ```bat
   git add .
   git diff --cached --stat
   git commit -m "Initial version"
   git branch -M main
   git remote add origin https://github.com/LOGIN/REPO.git
   git push -u origin main
   ```

   Если Git просит имя и почту, задайте их для этого репозитория и повторите коммит:

   ```bat
   git config user.name "Ваше имя"
   git config user.email "Ваша почта GitHub"
   ```

3. На вкладке **Actions** дождитесь зелёного результата **Build DOCX**.
   Внутри успешного запуска доступен артефакт `article-docx` с документом.
4. Для первого выпуска выполните:

   ```bat
   git tag -a v1.0.0 -m "Version 1.0.0"
   git push origin v1.0.0
   ```

   Workflow соберёт документ из этого тега и создаст **Release v1.0.0**
   с вложенным `article.docx`. Создавать этот релиз вручную заранее не нужно.
   Каждый новый выпуск получает новый тег.

Исходники, рисунки, `reference.docx` и настройки сохраняются в Git.
Готовый `article.docx`, PDF и папка `pandoc/` исключены через `.gitignore`.
При обычном HTTPS-подключении Git может открыть вход в GitHub через браузер.

## Версии и CI/CD

Версия хранится в теге Git. Используйте схему `vMAJOR.MINOR.PATCH`:

- `v1.0.1` — исправления текста или оформления;
- `v1.1.0` — новый материал или новые возможности сборки;
- `v2.0.0` — существенная переработка структуры или способа работы.

Перед новым тегом сохраните и отправьте изменения:

```bat
git add .
git commit -m "Update article"
git push
```

При защите `main` изменения отправляются отдельной веткой через pull request.

CI запускается при push в `main`, pull request в `main`, отправке тега `v*`
и вручную через **Actions → Build documents → Run workflow**.
Он загружает Pandoc 3.12.1, проверяет SHA-256 архива, запускает тот же
`build.cmd` и сохраняет DOCX в артефакте на 14 дней. Word и Python не нужны.

CD запускается после успешной сборки при отправке тега `v*`: отдельное задание
создаёт GitHub Release и прикладывает DOCX именно из этой сборки.
Используется штатный `GITHUB_TOKEN`; отдельный персональный токен не требуется.
В локальном проекте дополнительных программ для публикации релиза не нужно.

Dependabot раз в месяц предлагает pull request с обновлениями версий Actions.
Обновление Pandoc выполняется отдельно: версия и SHA-256 указаны в workflow.

## Настройки репозитория

- **Settings → Actions → General:** разрешите Actions. Workflow использует
  официальные `actions/checkout`, `actions/upload-artifact`, `actions/download-artifact`.
  Права **Workflow permissions** можно оставить **Read repository contents and packages permissions**:
  право записи для задания публикации задано в самом YAML.
- После первого успешного CI в **Settings → Rules → Rulesets** создайте правило
  для `main`: **Require a pull request before merging**, обязательная проверка
  **Build DOCX**, **Block force pushes**, **Restrict deletions**.
  При работе в одиночку задайте **Required approvals = 0**. Доступность rulesets зависит
  от тарифа и видимости репозитория.
- В **Settings → General → Pull Requests** можно включить
  **Automatically delete head branches**.

Для нового изменения при защищённой `main`:

```bat
git switch -c update-article
git add .
git commit -m "Update article"
git push -u origin update-article
```

Затем создайте pull request на GitHub, дождитесь CI и выполните merge.
Перед выпуском новой версии обновите локальную `main`: `git switch main`,
затем `git pull --ff-only`.

Если выпуск не завершился, проверьте вкладку **Actions**. Если в **Releases**
остался черновик от неудачной загрузки, удалите только этот черновик и повторите
задание публикации. Опубликованные теги и релизы не переиспользуйте.

Для PDF откройте DOCX в Word и выберите **Файл → Сохранить как → PDF**.
